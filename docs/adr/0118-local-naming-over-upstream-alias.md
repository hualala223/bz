# ADR-0118: 域与符号命名沿用本地，上游别名只进 CONTEXT.md

日期：2026-09-13 ｜ 状态：已采纳

## 背景

两线对同一个域用了不同名字（ADR-0117 背景里的域重组分道扬镳的直接后果）：

| 实体 | 本地 | 上游 |
|---|---|---|
| 待办 | `todo` 域、`bz-todo-*`、`TodoItem` | `memo` 域、`bz-memo-*`、`MemoItem` |
| 文献盒 | `literature` 域、`bz-literature-*` | `knowledge` 域、`bz-knowledge-*` |
| 做题家 | 独立 `quiz` 域 | `review/quiz-core` 子模块 |
| 密码本 | 并入 `encrypt` | 独立 `password-vault` 域 |
| 回忆墙 | 独立 `diary-wall` 域 | `diary` 域内部 |

约束条件：

1. **命令 id 是外部裸调用约定**（AGENTS.md 铁律 2）——主页.js 等外部脚本按 `bz-todo-*`/`bz-literature-*` 裸调用，id 改名需同步外部。
2. **上游的命名方向本身不稳定**：上游 ADR-0117 刚把待办域「正名为备忘录」（`src/todo/`→`src/memo/`、`bz-todo-*`→`bz-memo-*`，且 ADR 自述「用户经多轮拷问，中途两次方向修正」）；上游 0078/0109/0110 也在 password-vault 独立↔并入之间来回过。追一个正在横跳的目标没有收益。
3. 改名收益仅是文档对齐，全部成本（外部脚本同步、热键重绑、设置键迁移、测试路径）落在本仓库与用户身上。

## 决策

1. **本地命名冻结**：域目录名、命令 id、设置键、CSS 类名、导出符号一律沿用本地现状，**不追上游**。
2. **上游引用进本地时改名为本地叫法**：import 路径、设置键、CSS 类名、导出符号按本地命名落位；改名的映射关系写进该吸收 ticket 的说明里，不散落在代码注释。
3. **CONTEXT.md 增设「上游别名（yeshimei/bz 线）」对照节**，作为**唯一**的上游别名登记处——代码、命令 id、设置键里不出现上游别名。
4. **例外**：上游文件与本地同名同物、且改动为纯新增（无命名分歧）时，原样搬入，不强制改名。

## 理由与边界

- **边界一**：本决策只冻结「名字」，不冻结「结构」。上游若把某能力放进了不同的域（如密码本在上游是独立域），吸收时仍可以只搬能力、落进本地既有域（encrypt），域边界不变。
- **边界二**：不禁止在 ADR / issue / CONTEXT 正文里出现上游名字——恰恰相反，那里必须写清楚（否则读者对不上号）。禁止的只是**代码与用户可见契约**里的上游别名。
- **边界三**：若将来必须改名（如外部脚本一并迁移），改名应是独立决策、独立 ADR，不因「上游这么叫」而改。

## 影响

- 吸收上游块时多一步「改名落位」，成本可控（多为机械替换 + 一处 import 路径）。
- 代价：本地与上游的代码无法直接 diff 复用（对不上名字）；接受，因为我们本就不 merge（ADR-0117）。
- `CONTEXT.md` 新节使「同一个东西有两个名字」这件事self-documenting，避免后续协作时把 `todo` 与 `memo` 当成两个域。
