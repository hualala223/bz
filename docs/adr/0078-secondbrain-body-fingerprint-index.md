# 第二大脑正文指纹索引：挪动/改 YAML 不重嵌（ADR-0078）

ticket 173：用户观察到文档在白名单内挪动文件夹后被整篇重新向量化（实际行为，非推测）。经 grill-with-docs 四问拍板：判定依据从「路径 + mtime」升级为「路径 + mtime + 正文指纹（bodyHash）」三层。

## 背景

增量索引（ticket 108）以待处理 = 「meta 无该路径条目 ∨ entry.mtime ≠ 文件 mtime」判定。meta 键是文件路径，挪动文件夹 = 新路径无条目 + 旧路径成孤儿 → 整篇重嵌。而分块自 ticket 110 起已剥离 frontmatter，YAML 区修改本就不进 embedding 文本，mtime 变化却会触发重嵌——两者都违背「内容没变就不该重嵌」的直觉。

## 决策

1. **正文指纹（bodyHash）**：`NoteEntry` 新增 `hash` 字段，对**已存 chunks 的文本拼接**做 FNV-1a 哈希。指纹口径 = 切块管线输出（frontmatter 已剥、标题已并入首块），与向量输入严格一致——hash 说没变，向量就真没变，无脱节例外。改名/改正文 → 首块含标题、指纹变 → 重嵌；改 YAML/仅 mtime 变 → 指纹不变 → 跳过。
2. **三层判定**（doRefresh）：mtime 未变 → 直接跳过（不算指纹，增量路径零新增开销）；mtime 变了 → 算新指纹与旧条目比对，一致 → 仅更新 mtime 登记不重嵌；不一致 → 重嵌。
3. **挪动 = 孤儿匹配迁移**：refresh 把「路径已不存在」的旧条目（孤儿）暂存为指纹池（指纹从已存 chunks 现算，不读文件），新路径文件分块后指纹命中池 → **继承旧条目 chunks 与向量（按旧路径源偏移拷贝）、迁移登记键**，全程不调 Ollama；未命中的孤儿照常清理。孤儿池只在单轮 refresh 内存活——删除仍是删除，仅「删 + 同指纹重建」恰好构成挪动时才继承。
4. **版本 9 → 10 迁移零成本**：v9 条目已存 chunks 文本，迁移在 load() 时对每个条目从 chunks 现算指纹、就地升版本并落盘，**不读文件、不清库、不重嵌**（.vec 格式不变直接复用）。只有 version < 9 才走既有「整库清空重建」路径。
5. **重复笔记不特判**：多个孤儿同指纹时任取其一迁移（向量内容相同，结果等价），其余照常清理。

## Considered and rejected

- 指纹覆盖「标题+正文」之外的方案：把标题排除在指纹外以让改名也不重嵌——被拒，指纹会与向量输入脱节（hash 说没变、向量其实变了），埋例外逻辑的坑。
- 按 chunk 粒度记录断点状态（先前 ticket 114 讨论的延伸）——维持整篇粒度，本地单 vault 规模不划算。
- v9→v10 升级时清库全量重嵌（既有版本升级惯例）——被拒：指纹可从已存 chunks 现算，迁移可以零成本，清库纯属浪费。
- 指纹用全文 hash 而非 chunks 拼接 hash——被拒：前者迁移时必须读盘算 hash，后者 load 即得；且 chunks 拼接与向量输入严格同口径。

## 存量数据兼容

`secondbrain.json` meta 段 version 9 → 10，`NoteEntry.hash` 为可选字段；v9 数据经 load() 就地补指纹升级，一次写盘，用户无感。`.vec` 二进制格式与行序不变式（键序 × chunks 数）不变。
