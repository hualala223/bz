# 定稿核验（post-commit audit）：设计层一致性与双向裁决

> 本文件定义：第 N 章已正式接纳入正史（候选 `promote` + 追踪事务 + `close` + `doctor` 全部闭环）**之后**，对已定稿正文做一次独立的设计层一致性审计，并把每条出入交用户双向裁决（照设计改正文 / 照正文改设计），后者自动投影为跨产物修订计划。
> 触发词：**「本章已定稿，请核查」**，或「定稿核验 第N章」。接纳闭环完成后由主线程顺带提示一次可选项。
> 与「章后核查闭环」（`chapter-review-loop.md`）的关系：那是候选稿阶段的质量/文风交互闭环（去 AI 味、语言、错别字、距离、衔接），本协议是**定稿后**的语义对账，不重复其检查项，也不做文风判断。
> 本协议只读已提交产物 + 写报告，**不自动修改任何正文、大纲或设定**；所有修改都走裁决后的既有修订门禁。

---

## 一、前置条件与执行者

1. 运行 `chapter_candidate.py check`，确认第 N 章已提交（`last_committed_chapter ≥ N`）。未闭环时先走接纳流程，不审计候选稿。
2. `revision-governor` 等 custom agent 在 ZCode 3.3.4 不可用，本审计由主线程 solo 执行，结果中报告 `Fallback: project custom agents unavailable -> solo`。
3. 审计是语义任务，没有纯脚本判定；`scripts/post_commit_audit.py` 只负责报告结构校验和修订计划投影。

## 二、审计输入（定点读，不整读追踪）

| 文件 | 用途 |
|---|---|
| `正文/第{N}章_*.md` | 被审计对象（已定稿正文） |
| `大纲/细纲_第{N}章.md` | 本章计划：五段式、情节安排、人物关系与出场顺序、情节细化、结尾钩子 |
| `大纲/卷纲_第X卷.md`（当前卷，选读） | 当前剧情单元「本批可释放 / 严禁提前释放」边界 |
| `设定/角色/{本章角色}.md` + `追踪/角色状态/{名}.md` | 静态人设红线 + 动态当前快照 |
| `追踪/伏笔.md`、`追踪/上下文.md` | 当前视图（只读对照） |
| `追踪/逐章记录/第{N}章.md` | 本章已提交增量：正文实际写出的结果是否与对追踪的承诺一致 |
| 相关 `设定/` 世界规则、`追踪/长期事实.md`（按需定点） | 规则/物权/权限/不可逆状态对照 |

## 三、审计口径（防误报）

- **细纲字段只定「发生什么」，不定正文形状**：情节点自由合并、穿插、重排、演成场景（`workflow-daily.md`「从细纲到正文」）一律不算出入。判出入看事件与状态变化是否发生、因果是否同向，不看镜头顺序与写法。
- 每条判定输出三段：**标准条目 → 本案例对照 → 结论**，不得直接给结论。
- 严重级：
  - **S1 硬冲突**：身世/血缘/亲属/物权/权限/世界规则/不可逆状态与设定矛盾；提前释放本阶段「严禁提前释放」的信息；破人设红线（`设定/角色` 明文红线或 `character-voice-anchor` 锚定卡核心项）；正文否定已登记伏笔的存在或性质。
  - **S2 语义出入**：细纲承诺的情节点缺失/被替换；关键转折或高潮未发生；章尾钩子缺失/死钩；承诺伏笔漏埋；正文出现未登记的新伏笔；本章关系变化与细纲登记不符；行动成本/收益归属错配且影响后续。
  - **S3 可接受偏差**：写作自由范围内的变形，记录备查，不进裁决。
  - S4 风格类不属于本审计（候选阶段已闭环）；审计中发现新风格问题只提示一句，不展开。

## 四、审计维度（逐项过，每项给 ✓ / 出入条目）

| # | 维度 | 对照来源 |
|---|---|---|
| 1 | 五段式兑现（起因/发展/转折/高潮/结尾是否都发生、因果同向） | 细纲「内容概括」 |
| 2 | 多线推进（主线/辅线/事件线/感情线/逻辑线有无缺失、凭空新增承载后续的线） | 细纲「情节安排」 |
| 3 | 人物言行 vs 人设（动机、能力边界、语言特征、红线） | `设定/角色/{名}.md` + `追踪/角色状态/{名}.md` |
| 4 | 本章关系变化 vs 登记 | 细纲「人物关系和出场顺序」+ 逐章记录 |
| 5 | 世界规则/物权/权限/不可逆状态使用 | 相关 `设定/` + `长期事实.md` |
| 6 | 伏笔埋设/强化/回收 vs 登记（含新伏笔漏登记） | 细纲「本章兑现与状态变化」+ `追踪/伏笔.md` |
| 7 | 章尾钩子与 `下一章承诺` 是否仍成立 | 细纲「结尾设定和钩子」+ `上下文.md` |
| 8 | 阶段信息边界（是否提前释放） | 卷纲当前剧情单元 |
| 9 | 行动成本/收益归属 | 细纲「情节细化」 |

## 五、报告格式

报告落 `追踪/定稿核验/第{N}章_核验.md`（重复触发则整份重写，历史靠 ledger）。正文为人读的逐维度结论表，末尾必须有一个 ```` ```json ```` 围栏块供脚本解析：

```json
{
  "schema_version": 1,
  "kind": "post_commit_audit",
  "chapter": 12,
  "verdict": "clean 或 conflicts",
  "dimensions_checked": ["五段式", "多线推进", "人物", "关系", "世界规则", "伏笔", "钩子", "阶段边界", "成本收益"],
  "items": [
    {
      "id": "D001",
      "severity": "S1",
      "dimension": "人物",
      "location": "正文场景2 · 地牢对峙",
      "design_source": "设定/角色/林晚.md 红线第2条",
      "design_claim": "林晚不杀已投降者",
      "text_claim": "林晚处决了投降的巡卫",
      "direction": "fix_text 或 fix_design（S3 固定为 none）",
      "affected_entities": ["林晚"],
      "affected_fact_ids": ["K012"],
      "affected_chapters": [13, 14],
      "proposed_files": ["大纲/细纲_第013章.md"],
      "note": "裁决参考：若保留处决，13章复仇线动机需提前"
    }
  ]
}
```

字段规则：

- `items[].id`：`D` + 三位序号，报告内唯一。
- `severity` 只收 `S1/S2/S3`；S1/S2 的 `direction` 必须是 `fix_text` 或 `fix_design`（裁决前可先写建议值，报告交用户确认）；S3 固定 `none`。
- `affected_entities`：出入涉及的实体名（人物/势力/物件），供影响扫描按名命中；不得为规避扫描留空已知实体。
- `affected_fact_ids`：命中的 `K`/`R` 稳定 ID；尚无 ID 的新事实留空，ID 在修订事务中补建。
- `affected_chapters`：判断会波及的后续章号。
- `proposed_files`：`fix_design` 时必填非空——本轮要改的设计源文件（`设定/`、`大纲/` 下真实存在的文件，不含备份/归档）；`fix_text` 时留空（脚本自动定位正文文件）。
- `verdict` 与条目自洽：有 S1/S2 即 `conflicts`；`clean` 时不得有 S1/S2。

## 六、双向裁决门（硬门，不自动执行）

报告产出后**停下**，把每条 S1/S2 的「设计口径 vs 正文口径 + 两个方向各自的代价」列给用户，逐条等拍板：

- **fix_text（照设计改正文）**：走 `workflow-revision.md` 正文回炉闭环（`mode=revision` 追踪事务、伏笔/时间线/快照重算、`chapter_candidate.py sync`、声音画像 stale 处理、双门验收）。
- **fix_design（照正文改设计）**：先跑 `post_commit_audit.py project` 生成修订计划 JSON，再按 `workflow-revision.md` Step 1 走跨产物修订门禁（`revision-governor plan` solo → `revision_guard.py plan` 生成 `追踪/修改影响/active.json` → 联动修改设计文件 → `verify` → `revision_guard.py check` + `tracking_commit.py check`）→ 验收后恢复日更。
- **混合方向**：脚本按方向各生成一份计划；两份计划**串行**执行，任何时刻只允许一个活动事务，第一份验收关闭后再开第二份。

裁决参考原则（给建议，不代替用户）：读者已见事实优先于设计计划；已承诺的伏笔与期待优先于局部更优剧情；两边改动代价取小且自洽者；任何一边都不得静默覆盖另一边（`revision-impact-and-canon.md` 一.2）。

裁决完成后把每条 S1/S2 的最终 `direction` 更新回报告 JSON 块，再运行投影。

## 七、脚本

```text
# 校验报告结构与自洽性（裁决前/后都可跑）
python scripts/post_commit_audit.py validate --project {项目根} --input 追踪/定稿核验/第012章_核验.md

# 裁决完成后：按 direction 投影修订计划
python scripts/post_commit_audit.py project --project {项目根} --input 追踪/定稿核验/第012章_核验.md
```

`project` 输出：

- `追踪/定稿核验/第{N}章_修订计划_改设计.json`（有 fix_design 项时）——直接作为 `revision_guard.py plan --input`；
- `追踪/定稿核验/第{N}章_修订计划_改正文.json`（有 fix_text 项时）；
- 追加 `追踪/定稿核验/_ledger.jsonl` 一条记录（章号、结论、计划文件）。

计划生成后仍按 `workflow-revision.md` 全流程执行；脚本只省去手拼 JSON，不替代影响分析与复核。

## 八、干净结论

`verdict=clean`：报告落盘 + ledger 记录即完成，不产生任何修订，可直接续写下一章。报告本身是后续 `story-final-check` 与卷末冷读的对账凭证。

## 九、禁止的省事方式

- 把 S1/S2 写成 S3「记录在案」绕过裁决。
- 裁决完 fix_design 后不跑修订门禁，直接手改细纲/场景卡。
- 审计报告写完不落盘、只在对话里给结论。
- 用一次旧报告的 JSON 反复生成计划而不更新裁决结果。
