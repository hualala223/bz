# 256 — 上游 yeshimei/bz 增量吸收（Spec）

**状态：就绪待开工**

> 规则依据：ADR-0117（路线）、ADR-0118（命名）、ADR-0119（文档命名空间）、ADR-0120（吸收纪律与冻结清单）。
> 第一块的执行细节见 `issues/255-absorb-notice-settings.md`。

## Problem Statement

用户手里这条 bz 插件线是从 GitHub `yeshimei/bz` 分叉出来的，两边各走各的路——但这不是一次可以靠合并解决的「落后」，而是**方向已经不同**：

1. **上游有本地没有的能力**（通知偏好、锁屏、全域换肤、单源选择器、首页条目化……），但两线历史合不了（本地那次「并入上游」实际是内容复制，只有一个 parent），随手抄文件就会连对方的域重组一起带进来。
2. **随手抄的代价是本地踩坑换来的东西被覆盖**：存储层的空读防护是 4.9MB 数据被清成 `[]` 之后补上的；有个 core 导出牵着本地十几个调用点；日记写链路的文件在两边同名却是两套东西。抄错一次，可能是数据被清或编译全红。
3. **越往后越分不清谁是谁**：两边对同一个域叫不同的名字（todo/memo、literature/knowledge），ADR 编号从 `0106` 起彻底撞号——用户引用「ADR-0110」时已经无法确定指的是哪一件事。
4. **本地已有工作流不能被升级打断**：命令 id 是外部脚本的裸调用约定，改名等于用户的按钮/热键失效。

## Solution

先立四条规矩，再**一块一块**把上游看得上的能力搬过来；每一块都当独立改动做，出问题单独回滚。结果是：能力进来了，数据不用迁移，外部工作流不受影响，两边的文档各归各家。

规矩四条（已落 ADR）：

1. **定位**：同源分叉后的独立线，**单向取用**——不做 git merge、不回归上游主线、也不彻底分家；按块吸收，每块独立立项。
2. **命名**：代码、命令 id、设置键、类名一律用**本地叫法**；上游别名只登记在术语表里。
3. **文档**：上游的 ADR 与 issue 进独立命名空间归档（只读、保留原文件名），本地编号继续自己排；引用上游必须写明「上游 ADR-XXXX」。
4. **纪律**：A 类直接冲突一律**本地优先**；违反两条硬门槛（不得改数据契约、不得倒逼调用方改写）的块降级拆票；高风险文件列入冻结清单。

第一块选**通知四项设置**——它是审计里唯一「零调用方改动」的块。选它的目的不只是加功能，而是**把吸收流程完整跑通一遍**（摘取 → 按本地形态落位 → 补测试 → 过门禁 → 提交），之后按同一套流程处理其余块。

## User Stories

### 使用者：通知要能调

1. 作为插件的日常使用者，我想要能把常规通知降档成「只留警告与错误」，以便专注时不被琐碎提示打断。
2. 作为插件的日常使用者，我想要能把通知级别设为「仅错误」，以便在长时间专注写作时完全不被打扰。
3. 作为插件的日常使用者，我想要能调整通知的停留时长，以便文案长时看得完、文案短时别赖着不走。
4. 作为插件的日常使用者，我想要「常驻（点击才关）」这一档，以便需要核对的通知不被自动关掉。
5. 作为插件的日常使用者，我想要能选择通知从屏幕哪一个角弹出，以便它不遮挡我正在看的内容。
6. 作为插件的日常使用者，我想要能限制同屏最多显示几条通知，以便批量操作时不糊满整屏。
7. 作为插件的日常使用者，我想要超出上限时挤掉最旧的一条，以便总能看到最新状态。
8. 作为插件的日常使用者，我想要在移动端通知仍然是顶部居中，以便不因为桌面端设了某个角而在手机上错位。
9. 作为插件的日常使用者，我想要带「撤销」按钮的通知不受级别与时长设置影响，以便降噪之后反悔窗口依然可靠。
10. 作为插件的日常使用者，我想要常驻进度通知不被同屏上限挤掉，以便长任务的状态框始终在。
11. 作为插件的日常使用者，我想要在没改任何设置时插件行为与今天完全一致，以便这次升级不需要重新调习惯。
12. 作为插件的日常使用者，我想要在设置里一眼找到通知相关的项，以便不用在别的分组里翻。

### 使用者：升级不能伤到既有东西

13. 作为插件的日常使用者，我不想因为引入上游能力而迁移或重命名我的数据文件，以便我用别的工具/脚本读这些文件时不出错。
14. 作为插件的日常使用者，我不想因为升级而让我的复习记录、日记、收藏这类数据被清空或重写格式，以便我敢升级。
15. 作为插件的日常使用者，我不想因为升级而让我的第二大脑向量库被整库重嵌，以便不白等一次全量计算。
16. 作为插件的日常使用者，我不想因为升级而丢失番茄钟的历史记录，以便统计还能回看。
17. 作为插件的日常使用者，我不想因为升级而让我的命令热键与外部脚本失效，以便既有工作流原样可用。
18. 作为插件的日常使用者，我不想因为升级而让我的侧边面板/磁贴出现重复条目，以便界面不自相矛盾。

### 维护者：一块一块搬，别一次翻船

19. 作为维护者，我想要每次只吸收一个块并独立提交，以便出问题时能单独回滚而不牵动其他改动。
20. 作为维护者，我想要每块吸收都先明确「它会不会倒逼本地调用方改写」，以便不必等编译报错才发现。
21. 作为维护者，我想要每块吸收都有覆盖外部行为的测试，以便确认既有行为零回归。
22. 作为维护者，我想要有一份明确的「禁止被上游同名文件覆盖」清单，以便不重演清库事故与编译级中断。
23. 作为维护者，我想要每块都先跑一遍门禁（全量测试 + 类型检查 + 构建），以便基线始终是绿的。
24. 作为维护者，我想要在起步阶段串行做而不是多分支并行，以便不因为共享核心文件互相踩踏。
25. 作为维护者，我想要在吸收前把当前未提交的工作落成基线，以便吸收的改动能被单独审查。
26. 作为维护者，我想要每块吸收结束时更新进度记录与相关文档，以便下一次不用重新考古。

### 未来协作者（人或 AI 代理）：进来就得看懂

27. 作为未来的协作者，我想要能一眼分辨一条决策是本地做的还是上游做的，以便不误引、不误用。
28. 作为未来的协作者，我想要知道同一个域在两边分别叫什么，以便读上游代码不迷路。
29. 作为未来的协作者，我想要知道哪一侧的目录名是「同名不同物」，以便不做整目录覆盖。
30. 作为未来的协作者，我想要有一套现成的「摘取 → 落位 → 测试 → 门禁」流程可循，以便第二次吸收不用从零想。
31. 作为未来的协作者，我想要吸收范围由使用者圈定而不是自动追平上游，以便不引入没人要的功能。
32. 作为未来的协作者，我想要归档目录明确标注只读，以便不会顺手改上游文档。

## Implementation Decisions

### 规则层（约束所有块）

- 四条规矩见 ADR-0117 / 0118 / 0119 / 0120，为所有吸收工作的硬约束。
- **冻结清单**（吸收时禁止被上游同名文件覆盖）：存储层模块、移动端全屏辅助函数导出、日记写链路整套、第二大脑向量库版本常量、番茄钟模块、文献盒数据文件名、保险库模块、待办模块。
- **数据层三不**：不迁文件名、不裁历史、不动向量版本号。要动就先出「备份 + 就地迁移 + 回滚」独立票。
- **命名**：吸收上游文件时按本地叫法改名；上游别名只登记在术语表。通知这一块两侧键名无分歧，因此**原样沿用上游键名**。
- **例外通道**：任何块若必须修改本地导出签名、设置键语义、CSS 契约或数据格式才能落地，则该块拆成独立票并单独出 ADR，不得作为「纯增量」夹带。

### 第一块：通知四项设置

**新增四个设置键**（键名沿用上游，缺省值等于现状）：

| 键 | 语义 | 取值 | 缺省 |
|---|---|---|---|
| 通知级别 | 低档位静默常规通知；带操作按钮的通知不受影响 | 全部 / 仅警告与错误 / 仅错误 | 全部 |
| 停留时长 | 长文案自动延长；撤销类反悔窗口不受影响 | 干脆(2s) / 标准(3s) / 从容(5s) / 常驻(点击才关) | 标准(3s) |
| 弹出位置 | 桌面端四角任选，移动端恒顶部居中 | 右上 / 右下 / 左下 / 左上 | 右上 |
| 同屏上限 | 超出时挤掉最旧一条 | 3 / 5 / 8 | 5 |

- **通知模块**：新增一个读取当前偏好的内部通道，走既有的设置读取接口（不新增全局状态、不挂 window）；在**四个既有消费点**接入——级别门控、单条停留时长、弹出位置、同屏上限。**模块对外导出面保持不变**（两侧导出清单已核对一致），因此这一块不动任何调用方。
- **设置 schema**：新增一个「通知」分组并入主设置 schema。
- **界面接入形态（按本地现状，不抄上游形态）**：
  - 主设置页的组头有「卡片组（带图标）」与「区块标题平铺」两种形态，本地现用平铺形态（AI 区块即为平铺）。通知组沿用**平铺**形态接入，不引入图标字段改变既有版式。
  - 设置面板的导航是**按域组织**的；通知偏好属核心横切项、不建业务域，因此**不进设置面板导航**，只进原生设置页。上游那套「通知独立成面板一页」的做法本地不适用。
- **不做**：不动通知的图标表与既有通知类型；不在通知模块里引入上游其他横切偏好。

### 文档与命名空间

- 上游 ADR 归档目录与上游 issue 归档目录均为**只读**，保留上游原文件名（含重号与不规范命名）；本地编号继续连续发放。
- 双边同名同内容的 ADR（共同祖先期产物）不归档，仍平铺。
- 术语表新增「上游别名」节（七行对照 + 一条「同名不同物」警告）。

## Testing Decisions

**好测试的标准**：只断言**外部可观察行为**——弹出几条、停多久、在哪个角、被级别门控挡住没有——以及既有契约里本就对外可见的 DOM 类名（现有通知测试即按此断言）。禁止断言内部私有函数、内部字段名或实现路径；新增实现细节不写进测试。

**测试缝隙（seam）**：**不新增 seam**，直接复用既有的通知模块测试缝隙——即通过通知模块的公共入口（`notice()` / `notify()` 系列）驱动，配合设置快照注入来改四项偏好。这是可用的最高缝隙：它同时覆盖了级别门控、时长、位置、上限四条链路，而无需触碰通知模块内部。

**要覆盖的行为**：

1. 四项偏好均未设置时，通知行为与现状逐条一致（回归基线）。
2. 级别降档：低档位下常规通知不出；带操作按钮的通知仍出。
3. 时长四档与「常驻（点击才关）」生效；长文案动态延长仍优先于档位。
4. 位置四角生效；移动端仍顶部居中（不因偏好错位）。
5. 同屏上限生效且挤掉最旧一条；常驻进度通知不被挤掉。
6. 撤销类通知的反悔窗口不受级别与时长影响。

**先做的前置动作**：两侧同名测试文件先做一次比对，取并集后再补本地缺失的用例，避免漏掉上游已覆盖的边界（尤其「常驻帧不被挤出」「去重窗口」这类既有约束）。

**不做测试的部分**：本块无数据层改动，因此不新增数据层测试；不新增 UI 面板测试（本块不触碰设置面板导航）。

**既有同类测试可作范本**：核心层的设置 schema 与通知模块测试（当前通知测试已覆盖类型/时长/堆叠/去重/常驻/便捷模板等外部行为）。

## Out of Scope

- **其他吸收块**：锁屏、单源选择器（路径弹窗单源与列表行单源）、全域换肤、首页条目化、剪藏本渲染单源、影院豆瓣队列、知识盒的术语来源与视频元数据、原型/行为单源体系——均由使用者圈定后另立票。
- **A 类 15 项直接冲突**：按 ADR-0120 一律本地优先，不因吸收而改变。
- **不做的事**：不 merge、不回归上游主线、不向反方向推送本地成果；不追平上游全部功能面。
- **数据侧**：不迁移/重命名任何数据文件、不裁剪番茄钟历史、不改动向量库版本号、不改动 vault 文件结构（含日记章节层级）。
- **界面侧**：不引入上游的设置面板独立导航页机制；不改动主设置页既有的组头版式契约。
- **工程侧**：本次不调整构建脚本、不调整 lint/格式约定、不做仓库卫生清理（根目录遗留物单独处理）。
