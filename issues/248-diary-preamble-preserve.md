# issue 248：日记前导区保留——模板形态文件不再让「写日记」被守卫拒写（ADR-0110）

## 报障

用户 2026-09-11 报「没成功」，截图通知：

> 「2026-09-11」有 28 行内容无法解析，本次修改没有写入文件（直接处理会丢失这些行）。
> 请先在日记本设置中运行「检测日记解析」修复后再试。

## 定位

真实 vault 的 `我的/日记/2026-09-11.md` = **模板形态**（用户 QuickAdd 模板/宏创建）：
frontmatter + `## 睡眠相关/## 随笔/## 新闻联播内容记录/## 日常行为记录/## 日程规划` 骨架 + 日程规划三段模板，共 **28 行非空内容、0 个条目标题**。

链路：

1. `parseFile` 的口径是「首个条目标题行之前的非空行全部计入未解析行」→ 整篇 28 行全中；
2. P0 写前守卫 `refuseIfDiskUnparsed`（`git log -S` 溯源：上游线并入，`a9a07ca4`）命中即拒写 → `addEntry` 全链路（写日记 / 每日复盘 / 日程规划）失败；
3. 通知引导的「检测日记解析」**救不了这种文件**：`scanUnparsed` 把整篇列进「需手动处理（28 行）」且只提供跳转定位，无任何可执行动作 → 守卫与修复工具互相指认，**死锁**；
4. 统计面：全库 621 个日记文件，**153 个**是模板形态、仅 4 个含 `# emoji HH:mm` 条目头——用户的主力数据全在守卫的拒写面内。

即：这不是「偶发脏数据」，而是**条目模型与用户模板长期共存产生的结构性冲突**；旧版（无守卫）表现为「写一次抹掉一次骨架」（样例 `2026-09-10.md` 已无骨架），新版表现为「完全写不进去」。

## 修复（ADR-0110）

日期文件分「前导区 + 条目区」，前导区写回时原样保留：

- `src/diary/parser.ts`：新增 `findEntryRegionStart`（首个**疑似条目标题行**：合法形 / 缺空格形 / 时间非两位形）+ `extractPreamble`（前导区文本，仅收敛首尾空行）；`parseFile` 的未解析行口径收窄为**条目区内**孤行；三款标题正则导出（`HEADING_RE`/`NO_SPACE_HEADING_RE`/`SHORT_TIME_HEADING_RE`）；
- `src/diary/store.ts`：`refuseIfDiskUnparsed` → `guardDiskRead`（返回 `{ refused, preamble }`，守卫读与前导区同一次读）；`writeFile` 写回 = 前导区 + 空行 + 条目块，行号戳加 `preambleOffset`；条目清空时前导区存在则只收回条目区、文件保留（无前导区才整文件删除）；`deleteEntry` 同口径；
- `src/diary/repair.ts`：`scanUnparsed` 跳过前导区（不报「需手动处理」），标题正则改从 parser 导入（原先两处复制、有口径漂移隐患）；
- 口径自动随单源收窄的下游：`loadAll`/`refreshFile` 未解析警告、`recap/summarize` 写前预检。
